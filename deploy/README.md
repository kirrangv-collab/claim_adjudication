# Deploy ClaimLab as a public website, for free

This folder is a complete, production-style deployment kit:

| File | What it does |
| --- | --- |
| [docker-compose.yml](docker-compose.yml) | Caddy (HTTPS) → web (nginx + React UI) → api (FastAPI) → PostgreSQL. The `full` profile adds Qdrant + Neo4j. |
| [Caddyfile](Caddyfile) | Automatic Let's Encrypt certificate, HTTP→HTTPS redirect, HSTS, compression. |
| [.env.example](.env.example) | Every setting, documented. The real `.env` is generated by `configure.sh` and never committed. |
| [setup-server.sh](setup-server.sh) | Prepares a fresh Ubuntu server: Docker, firewall ports 80/443, swap on small machines. |
| [configure.sh](configure.sh) | Writes `deploy/.env` with strong random secrets. |
| [backup.sh](backup.sh) / [restore.sh](restore.sh) | Compressed PostgreSQL dumps (14-day retention) and restore. |
| [reset-demo.sh](reset-demo.sh) | Nightly wipe of reviews/evaluations for public demos. Accounts are kept. |
| [update.sh](update.sh) | Back up, `git pull`, rebuild and restart. |

The recommended free setup is shown below. Each part costs $0:

```
visitor ──HTTPS──▶ Caddy :443 ──▶ web (nginx, UI) ──/api/──▶ api (FastAPI) ──▶ PostgreSQL
            │  Let's Encrypt                                    └─(full)─▶ Qdrant, Neo4j
   your-name.duckdns.org  (free DNS)          Oracle Cloud "Always Free" VM (free server)
```

* **Server:** an Oracle Cloud Always Free VM. The Ampere A1 Arm shape gives up to 4 CPUs and 24 GB RAM in total.
* **Domain:** [DuckDNS](https://www.duckdns.org).
* **TLS certificate:** Let's Encrypt, obtained and renewed automatically by Caddy.
* **Container images:** built on the server, or pulled from GitHub Container Registry. GHCR is free for public repos.

Two stack sizes:

| Stack | Services | RAM used (measured) | Use it on |
| --- | --- | --- | --- |
| `lite` (default) | caddy, web, api, db. Vector index and knowledge graph run in memory inside the API. | ≈ 150 MB idle | Any VM, even 1 GB |
| `full` | lite + Qdrant + Neo4j (real vector DB and graph DB) | ≈ 1.2 GB idle (Neo4j ≈ 800 MB) | A1 Flex with ≥ 4 GB |

Both stacks produce the same adjudication decisions. `/api/v1/config` reports which knowledge backends are active and lists any fallback.

## 1. Create the free server (Oracle Cloud)

1. Sign up at <https://www.oracle.com/cloud/free/>.
   * A credit or debit card is needed for identity verification. Always Free resources are not charged.
   * Your **home region** cannot be changed later. Pick one near your users that has Ampere A1 capacity.
2. **Compute → Instances → Create instance**:
   * **Image:** Canonical Ubuntu 24.04 (or 22.04).
   * **Shape:** *Ampere → VM.Standard.A1.Flex*. Use 2 OCPU / 12 GB, or up to 4 / 24, which is still free.
   * **Networking:** keep "Assign a public IPv4 address" on.
   * **SSH keys:** upload your public key, or download the generated private key.
   * If you get **"Out of capacity"**, retry later, try another availability domain, or choose the
     always-free **VM.Standard.E2.1.Micro** (1 GB RAM) and use the `lite` stack. `setup-server.sh` adds swap automatically.
3. **Open ports 80 and 443 in the cloud firewall.** Go to the instance → *Subnet* → *Security Lists* →
   *Default Security List* → **Add Ingress Rules**:
   * Source `0.0.0.0/0`, TCP, destination port `80`
   * Source `0.0.0.0/0`, TCP, destination port `443`
   * Optional: Source `0.0.0.0/0`, UDP, destination port `443` (HTTP/3)
4. Optional: make the IP permanent with *Networking → Reserved public IPs*, then attach it to the instance.
   The default ephemeral IP stays the same until the instance is terminated.

> Oracle may reclaim Always Free instances that stay almost completely idle for 7 days. A site with
> regular visitors, plus the nightly backup/reset cron jobs, normally avoids this. Upgrading the
> account to *Pay As You Go* removes reclamation. Always Free resources are still free on that plan;
> set a budget alert to be safe. See Oracle's
> [Always Free resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm).

## 2. Get a free domain (DuckDNS)

1. Sign in at <https://www.duckdns.org> with GitHub, Google, etc.
2. Add a subdomain, e.g. `claimlab-yourname`, and set its IP to the VM's **public IP**.
3. Check it: `nslookup claimlab-yourname.duckdns.org` should return that IP.

Already own a domain? Create an `A` record pointing at the VM instead. Cloudflare DNS works too.
Keep the proxy **off** (grey cloud), or switch it on only after the certificate has been issued.

## 3. Install and start ClaimLab

SSH into the server (`ssh ubuntu@<public-ip>`) and run:

```bash
git clone https://github.com/kirrangv-collab/claim_adjudication.git
cd claim_adjudication

sudo bash deploy/setup-server.sh          # Docker, firewall 80/443, swap if RAM < 3.5 GB
exit                                      # log out and back in so the docker group applies
```

```bash
cd claim_adjudication
bash deploy/configure.sh --domain claimlab-yourname.duckdns.org            # lite stack, public demo on
#   options: --stack full   --no-demo   --demo-password 'something-else'

cd deploy
docker compose up -d --build              # first build: ~5-10 min on A1, longer on E2.1.Micro
docker compose ps                         # all services "healthy"
docker compose logs -f caddy              # watch for "certificate obtained successfully"
```

Open **https://claimlab-yourname.duckdns.org**. The certificate is issued on the first start and renewed automatically.

Create your own admin account. It is not shown on the login page, and you choose the password interactively:

```bash
docker compose exec api python scripts/create_user.py --username admin --role admin
```

### Public demo mode

`configure.sh` turns on **public demo mode** by default (`CLAIMLAB_PUBLIC_DEMO=true`):

* The login page shows two shared reviewer accounts, `demo-maker` and `demo-checker`, with their password
  (default `try-claimlab`) and one-click sign-in buttons. Visitors can then try the full maker–checker
  workflow: one account submits, the other approves.
* A banner in the app reminds visitors that the data is shared and synthetic.
* The accounts are (re)created on every API start and by `reset-demo.sh`. They only have the reviewer role.

Use `--no-demo` for a private deployment; create users with `scripts/create_user.py` instead.

Keep `CAF_MODEL_API_KEY` empty on a public site. Otherwise visitors spend your Gemini quota. The
five-agent pipeline is fully deterministic without it.

## 4. Scheduled jobs (backups, nightly demo reset)

Run `crontab -e` as the `ubuntu` user and add:

```cron
15 3 * * * bash /home/ubuntu/claim_adjudication/deploy/backup.sh     >> /home/ubuntu/claimlab-backup.log 2>&1
30 3 * * * bash /home/ubuntu/claim_adjudication/deploy/reset-demo.sh >> /home/ubuntu/claimlab-reset.log  2>&1
```

* Backups go to `deploy/backups/claimlab-YYYYMMDD-HHMMSS.sql.gz`. Copies older than `KEEP_DAYS` (default 14) are deleted.
  Copy them off the server now and then (`scp`, or Oracle Object Storage, which includes 20 GB free).
* Restore with `bash deploy/restore.sh deploy/backups/<file>.sql.gz`. It asks you to type `restore`;
  add `--yes` for scripts.
* Drop the `reset-demo.sh` line if the site is not a public demo.

Optional free uptime monitoring: add `https://<your-domain>/api/v1/health` as an HTTP monitor in
[UptimeRobot](https://uptimerobot.com) or similar.

## 5. Updating

```bash
bash ~/claim_adjudication/deploy/update.sh     # backup → git pull → rebuild → restart → prune
```

### Using pre-built images instead of building on the server

The [Release images](../.github/workflows/release-images.yml) workflow publishes multi-arch
(amd64 + arm64) images to GitHub Container Registry. It runs when a `v*` tag is pushed, or manually from the
Actions tab. The images are:

* `ghcr.io/<owner>/claimlab-api`
* `ghcr.io/<owner>/claimlab-web`

After the first run, make both packages **public** under *GitHub → your profile/org → Packages →
Package settings*. Then add to `deploy/.env`:

```bash
API_IMAGE=ghcr.io/kirrangv-collab/claimlab-api:latest
WEB_IMAGE=ghcr.io/kirrangv-collab/claimlab-web:latest
```

`docker compose pull && docker compose up -d` (or `update.sh`) now skips the build. This is the best option for 1 GB VMs.

## 6. Test the kit locally (Windows, macOS, Linux)

Docker Desktop is enough to run the exact production stack:

```bash
bash deploy/configure.sh --domain localhost       # Windows: use Git Bash
cd deploy && docker compose up -d --build
```

* Open `https://localhost`. Caddy uses its own local certificate authority, so the browser warns once.
* To skip TLS for a quick browser test, start Caddy with a plain-HTTP site address:
  `DOMAIN=http://localhost docker compose up -d caddy`, then open `http://localhost`.
* If ports 80/443 are busy, add `HTTP_PORT=8080` and `HTTPS_PORT=8443` to `.env`.
* Clean up with `docker compose down -v`. `-v` deletes the database volume, and is needed if you regenerate `.env`,
  because PostgreSQL keeps the password it was first created with.

## Security checklist

The kit already provides:

* HTTPS only, with HSTS; the HTTP→HTTPS redirect is handled by Caddy.
* CSP, `X-Frame-Options`, `nosniff` and `Referrer-Policy` headers; the server banner is removed.
* Only Caddy publishes ports. Database, API, Qdrant and Neo4j are reachable only on the internal Docker network.
* Every container runs with `no-new-privileges` and rotated logs. The internet-facing web and api containers also
  run as non-root, with read-only root filesystems and all Linux capabilities dropped. Caddy keeps only `NET_BIND_SERVICE`.
* Random secrets. The API refuses to start in production with the default JWT secret, and `/docs` is disabled.
* Per-IP rate limiting on write requests. `FORWARDED_ALLOW_IPS` trusts only the internal proxy subnet, so the
  real visitor IP is used and spoofed `X-Forwarded-For` headers are ignored.
* Maker–checker review: the account that submits a case cannot approve it.

Your responsibilities:

* Keep the OS patched. Ubuntu enables `unattended-upgrades` by default; reboot occasionally.
* Use SSH keys only. Oracle images disable password login by default.
* Never put real patient data on the site. ClaimLab is a research prototype; see the main README.
* Protect `deploy/.env` (mode 600) and back it up somewhere private. Losing it means losing database access.

## Troubleshooting

| Symptom | Fix |
| --- | --- |
| Browser can't connect at all | Check the cloud security list (step 1.3) and that `setup-server.sh` ran (`sudo iptables -L INPUT -n` shows ACCEPT for 80/443 above the REJECT). |
| Caddy log: `challenge failed` / `no such host` | DNS not pointing at the VM yet (`nslookup`), or port 80 blocked. Fix it, then `docker compose restart caddy`. Avoid many restarts in a row: Let's Encrypt rate-limits failures. |
| `api` unhealthy, log says `password authentication failed` | `.env` was regenerated after the database was created. Restore the old `.env`, or run `docker compose down -v` (**deletes data**) and start again. |
| `required variable POSTGRES_PASSWORD is missing a value` (or `DOMAIN`, `JWT_SECRET`) | Run `configure.sh`, and run `docker compose` from the `deploy/` directory so it reads `deploy/.env`. |
| Build killed / very slow on a 1 GB VM | Make sure swap is on (`swapon --show`), or use pre-built GHCR images. |
| Neo4j restarting | Not enough RAM for `full`. Switch to `lite`: set `COMPOSE_PROFILES=` and both backends to `memory` in `.env`, then `docker compose up -d --remove-orphans`. |
| Login says "Too many requests" | Per-IP write limit (60/min). Raise `RATE_LIMIT_REQUESTS` in `.env` if needed. |
| Service status | `docker compose ps`, `docker compose logs --tail 100 api`, `curl -s https://<domain>/api/v1/health` |

## Other free or cheap hosting options

* **Any VPS** (Hetzner, DigitalOcean, Lightsail, a home server with port forwarding): the same steps from section 3 apply unchanged.
* **Self-hosted PaaS** (Coolify, Dokku, CapRover) on that VPS: point it at `deploy/docker-compose.yml`.
  Remove the `caddy` service if the PaaS provides its own proxy.
* **Free PaaS tiers** (Render, Fly.io, Hugging Face Spaces) can run the API and UI. They usually sleep when idle and
  lack persistent PostgreSQL, so the review queue would not survive restarts. That is fine for a stateless demo of
  `/api/v1/adjudications`, but not for the full workflow.

## Before making the repository public

* [ ] Decide whether to publish `Claim adjudication_progress.pdf`. It is a progress report and may contain local paths and names.
* [ ] An earlier commit added, and a later one removed, `data/combined-ca-bundle.pem`. It is a bundle of *public*
      CA certificates, with no private keys, but it reveals corporate PKI. It is still in git history. To purge it,
      coordinate with all collaborators, because history is rewritten and everyone must re-clone:

      pip install git-filter-repo
      git filter-repo --path data/combined-ca-bundle.pem --invert-paths
      git push --force --all && git push --force --tags

* [ ] Enable *Settings → Code security → Private vulnerability reporting* (used by [SECURITY.md](../SECURITY.md)),
      Dependabot alerts and secret scanning.
* [ ] Set the repository description, topics and website URL, and choose *Settings → General → Features* (Issues, Discussions).
* [ ] Tag a release (`git tag v0.3.0 && git push --tags`) to publish the container images.
